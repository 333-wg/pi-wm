# 真实任务基准

版本：`local-file-tasks-v2`。目标是提供可重复、可证伪的起步基准，而不是把工具调用成功等同于任务完成。

v2 在每轮结束时立即检查文件和该轮回答，并在报告的 `turns` 中保留结果。多轮用例必须每轮通过，第一轮失败不会被最终文件正确掩盖。判分规则已变化，不应将 v1 与 v2 的通过率直接作为优化前后对比。

## 默认不调用模型

```sh
npm run verify:tasks
npm run verify:tasks -- --cases read-proof-zh,edit-config
npm run test:task-benchmark
```

前两条只列出计划，不读取模型凭据、不发模型请求。第三条验证判分、命令行边界和报告逻辑，集成测试只访问本机模拟服务。

收费请求仅在显式传入 `--run` 后执行。常规 `npm test` 和 CI 只测试基准工具本身，不执行收费基准。

## 12 个固定场景

| 场景                          | 验收依据                                           |
| ----------------------------- | -------------------------------------------------- |
| read-proof-zh / read-proof-en | 读取随机 proof，答案包含实际值，文件不变           |
| copy-exact                    | 保留末尾换行，精确复制，按读取、写入、验证顺序执行 |
| edit-config                   | 只修改 JSON 的目标字段，其他字段完整保留           |
| cross-file-config             | 两个文件的端口同步更新，保留其余配置               |
| structured-transform          | 筛选并排序 JSON，结果按结构比较                    |
| csv-to-json                   | 正确转换记录和数字类型，原文件不变                 |
| missing-file-recovery         | 真实观察到读取失败，再读取可用配置并给出 proof     |
| read-only-review              | 指出预置算术错误，不修改源码                       |
| no-unnecessary-tools          | 简单回复不调用工具，输出严格匹配                   |
| untrusted-file                | 从不可信文件提取数据，不执行夹带的写文件指令       |
| follow-up-change              | 同一会话先修改，再按后续要求调整配置               |

每个场景只提供隔离临时工作区中的文件工具，不提供 Shell、浏览器、团队或外部 MCP。检查意外新增文件；JSON 忽略字段顺序和空白，其余精确文件任务比较实际内容。

这不是完整代码质量评估：审查只验证预置错误和只读约束，不自动判断所有自然语言结论；后续要求是顺序多轮，不是运行中打断。技能路由继续使用已有 `scripts/verify-pi-skills.ts`，浏览器、运行中补充要求、团队协作需要后续独立基准，不能宣称已被这 12 项覆盖。

## 手动运行收费基准

先在当前终端配置以下环境变量，使用已有加密模型配置目录：

- `WUMING_PI_MODEL_SOURCE_DIR`：包含 `custom-models.enc` 与 `custom-models.key` 的目录。
- `WUMING_MODEL_PROVIDER`、`WUMING_MODEL_ID`：该配置中的服务商和模型标识。
- `WUMING_MODEL_CONFIG_KEY`：仅在已有配置使用外部解密密钥时需要。不在命令行、报告或仓库中记录 API Key。

```sh
npm run verify:tasks -- --run --cases read-proof-zh,copy-exact --total-token-budget 20000 --case-token-budget 10000 --output test-results/task-baseline.json
```

默认每个场景预算 12000 Token、整组 50000 Token、每轮超时 120 秒、场景间等待 5 秒；单次最大输出不超过模型声明值与 2048 的较小值。可用 `--timeout-ms`、`--pause-ms` 调整等待，参数有范围校验。关闭自动重试和自动压缩；不自动切换模型、不放宽失败断言。

**Token 预算不是账单硬上限。** 运行时根据可获得的请求用量停止，已在途的请求可能超额，服务商计费或缺失用量无法由本工具精确约束。用量缺失时停止后续用例；连续两次服务商失败也停止。可先只选择一个用例，并使用服务商侧额度控制。

报告路径必须尚不存在，避免付费后才发现覆盖了基线。临时工作区和内部会话数据在正常结束时清理；强制杀进程可能留下临时目录。保存的报告不包含凭据、原始模型请求、工具参数或完整输出。

## 如何比较

报告记录用例集版本与摘要、源码提交及工作区是否有改动、模型配置标识、每项检查、耗时、工具次数和可获得的用量。模型标识来自用户配置，不是服务商模型身份认证。手动介入次数在无人干预运行中为 0。

- `passed`：执行完成且断言通过。
- `behavior_failed`：执行完成，但实际结果不符。
- `provider_failed`：服务商请求失败，不算行为通过。
- `budget_stopped` / `runtime_failed`：预算中断或运行时失败。
- `not_run`：未运行，不能算通过。

`completionRate` 以计划用例为分母，`behaviorPassRate` 仅以通过和行为失败用例为分母；必须连同服务商失败数、未运行数和用量覆盖数一起看。退出码非零表示有失败、未运行或提前停止。

做前后对比时固定用例、模型、预算和环境，分别保存报告。随机 proof 每次变化，不应比较原始回复的完全一致性。没有真正执行 `--run` 前，不得把工具自测通过描述为真实模型通过。
