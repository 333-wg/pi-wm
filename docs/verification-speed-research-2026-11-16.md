**任务收尾验证提速：GitHub 调研与 Pi-Wuming 落地建议**

调研日期：2026-11-16。范围：编码 Agent 的任务收尾、浏览器验证，以及本仓库测试流程。本文是调研与设计建议，没有修改运行时策略、技能、测试配置或 CI。

核心建议：依据改动的实际风险选择最小充分验证，把已知的操作和结果检查合并执行，复用仍然有效的证据，满足验收条件后立即结束。模型更强可以成为评估新策略的动机，但不能单独作为免检依据。

本次查阅了 GitHub 项目的源码、官方文档、发布记录和问题讨论，并与本仓库实现交叉检查。另按用户补充要求重点检查了 DeepSeek Harness、OpenAI Codex 和 Anthropic 的 Claude Code 文档及公开 harness 示例，见第十部分。没有对 Pi-Wuming 做耗时基准或抽查用户历史任务，因此以下内容区分了已经确认的机制、可能的耗时来源和待实测的优化收益；不承诺固定提速比例。

**一、先区分两种速度问题**

| 问题                                   | 用户感受到的等待     | 首要优化对象                                 |
| -------------------------------------- | -------------------- | -------------------------------------------- |
| Agent 已完成实现，还在浏览器里不断检查 | 每次任务都拖着不结束 | 验证选择、模型往返、停止条件、页面和证据复用 |
| 本仓库自动化测试、CI 或发布耗时长      | 提交或发布反馈慢     | 受影响测试选择、构建缓存、环境启动、执行隔离 |

当前诉求首先对应第一种。引入 Nx、增加 CI 并发，未必能减少 Agent 每次点击之后重新思考、截图和检查的时间。

收尾时间可以粗分为：环境准备 + 实际检查 + 模型调用与等待 + 取证传输 + 修复重试。只优化测试程序的执行速度，会遗漏其中几项。

**二、GitHub 上值得采用的机制**

| 项目与一手来源                                                                                                                    | 已确认机制                                                                                  | 对 Pi-Wuming 的价值与限制                                                                               |
| --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| [Aider 源码](https://github.com/Aider-AI/aider/blob/main/aider/args.py)、[官方说明](https://aider.chat/docs/usage/lint-test.html) | `auto-lint` 默认开启，`auto-test` 默认关闭；测试可配置或主动调用                            | 将廉价检查和完整测试分开。它证明这种产品取舍已有实践，但不证明默认关闭测试适合所有任务                  |
| [Vitest 4.1.9 CLI 文档](https://github.com/vitest-dev/vitest/blob/v4.1.9/docs/guide/cli.md)                                       | `related --run` 根据源码依赖选测试；`--changed` 根据 Git 变化选测试；配置变化可触发扩大范围 | 本仓库声明 Vitest 4.1.9，相关能力无需为了试用而升级主版本。变量形式的动态导入等不在可靠的静态关系范围内 |
| [Playwright CI 文档](https://github.com/microsoft/playwright/blob/main/docs/src/ci.md)                                            | `--only-changed` 利用测试依赖图做优先运行                                                   | 官方明确它是可能漏选的启发式，并建议之后保留完整测试。不能宣传为安全取代全部 E2E 的开关                 |
| [Microsoft Playwright CLI](https://github.com/microsoft/playwright-cli)                                                           | 采用面向编码 Agent 的 CLI 与技能接口，减少大工具描述和页面树对上下文的占用                  | 借鉴精简输出和持久会话；CLI 本身不保证更少调用、更短耗时，也无须立即替换现有 ego-browser                |
| [agent-browser 发布记录](https://github.com/vercel-labs/agent-browser/blob/main/CHANGELOG.md)                                     | 0.38.0 记录了快照增量、条件截图以及存活元素引用的复用                                       | 借鉴“变化才返回、只返回相关区域”。检测到画面变化不代表正确，未变化也不保证满足需求                      |
| [Turborepo 缓存设计](https://github.com/vercel/turborepo/blob/main/apps/docs/content/docs/crafting-your-repository/caching.mdx)   | 用输入指纹复用任务输出；明确依赖确定性输入                                                  | 借鉴验证证据缓存。输入遗漏会产生错误命中，外部网站、真实服务和变化中的数据不能仅凭代码没变就复用        |
| [dorny/paths-filter](https://github.com/dorny/paths-filter)                                                                       | 在 GitHub Actions 的 job/step 层按改动路径选择执行                                          | 可以低成本改善 CI，但路径匹配不理解行为和传递依赖，需要维护共享模块的扩大规则                           |

补充参考：[Nx affected](https://21.nx.dev/docs/features/ci-features/affected) 使用 Git 与项目图确定受影响项目，默认把锁文件变化视为影响全部项目。这种“普通改动缩小、共享输入扩大”的设计，比单看文件数量可靠。现阶段不建议仅为验证提速就迁移整个构建体系。

**三、一个与本次问题直接相关的反例**

[agent-browser #1351](https://github.com/vercel-labs/agent-browser/issues/1351) 的报告者在约 150 个案例中观察到：换用更省 token 的接口后，模型调用从 2,028 次增加到 3,351 次，约增加 65%，其中约 30% 的工具调用是快照。该讨论中的另一组小规模自报实验把动作、等待和快照合成一次返回，报告了更少轮次和更短耗时。

这些是社区自报结果，样本与本项目不同，也没有在此复现。它们支持一个值得验证的假设：减少模型往返可能比减少单次输出更有效；不能据此给 Pi-Wuming 承诺相同比例的提速。

例如，对一个步骤已经明确的保存流程，模型可一次提交“填写 → 保存 → 等待明确成功状态 → 返回相关区域与错误摘要”，然后根据结果决定是否继续。未知页面、意外跳转或失败仍需中途观察。没有必要每个机械动作都让模型重新规划。

**四、本仓库已经具备什么，还缺什么**

1. **已有较完整的效率原则，继续叠加提示词的收益可能有限。** `packages/pi-adapter/src/system-prompt.ts:305` 起已经要求最小充分检查、避免全量验证、避免人工重复自动化交互、复用环境，并在第 328 行给出浏览器约 60 秒目标与约 90 秒停止扩展的规划规则。它们不是跨工具的强制执行器。

2. **工具规则、技能和文档的范围并不完全统一。** 同一提示词第 173、187、197、212 行使用了较宽泛的前端验证要求；`.wuming/skills/frontend-verify/SKILL.md:12` 要求启动服务并检查控制台、交互、桌面和移动布局；`docs/agent-verification-workflow.md` 也保留了双视口流程。技能是否在具体任务中被加载尚未核实，但一旦适用，这些文本可能把原本有限的任务扩大。`docs/verification-efficiency.md` 已采用更窄范围，应以统一策略同步其他入口。

3. **批量浏览器操作已存在，重点应转向使用率和返回体积。** `packages/sandbox/src/browser-workflow.ts` 实现了 1–12 步的批量动作、条件等待和失败停止；`packages/sandbox/src/browser.ts` 的批量路径返回最终快照、诊断以及耗时。下一步应测量 Agent 是否真的用到它、是否随后重复截图或诊断，而非再实现一个同类工具。

4. **当前验证守卫不是覆盖分析器，也没有证据表明它主动制造重试。** `packages/orchestrator/src/verification.ts` 识别 `write_file`、`edit` 后的部分工具调用和命令。成功的浏览器快照等即可满足“存在验证证据”的启发式；不代表某个行为通过测试。`orchestrator.ts:5293` 起的守卫只记录缺失警告，不阻塞完成，不自行启动新一轮验证。任意 shell 写入、部分自定义验证命令和外部浏览器 CLI 也可能不被正确分类。

5. **守卫的失效范围过粗。** 它围绕最后一次已识别编辑检查之后是否有证据，没有把证据绑定到具体文件依赖和验收目标。若先验证逻辑再修改无关文档，就难以表达“逻辑证据仍然有效”。这首先是证据模型的限制，不是已测得的耗时结论。

6. **仓库自身 E2E 有可单独优化的固定成本。** `playwright.config.ts` 设置单 worker；`e2e/edit-composer.spec.ts` 在 `beforeEach` 启动 Gateway 与 Vite，结束后关闭；根 `test:e2e` 先做完整 build，而共享 harness 启动的是源码 Gateway 和 Vite。这里有评估环境复用、构建必要性和测试隔离的空间，但不能未经隔离检查直接增加并发。当前 CI 已经只运行 6 个核心浏览器 spec，并取消同一 ref 的旧运行，不应把它描述成每次运行全量浏览器测试。

7. **失败时保留产物不等于失败时才开始记录。** 当前配置为 trace/video `retain-on-failure`，运行时仍有记录成本，成功后才丢弃。Playwright 的[官方建议](https://github.com/microsoft/playwright/blob/v1.62.1/docs/src/best-practices-js.md)讨论了 trace 成本及首次重试采集。项目核心配置的 retries 为 0，直接改成 `on-first-retry` 将没有自动 trace；要在首次失败取证价值与开销间做明确选择，不能机械替换。

**五、建议采用的默认验证策略**

默认提供“按风险验证”，根据受影响行为自动选择检查；“完整验证”可作为用户主动选项。不能因为模型自称有信心就跳过检查，也不必每次向用户询问选择哪个模式。

| 改动性质                                         | 默认必要检查                                     | 默认省略的工作               | 扩大条件                                |
| ------------------------------------------------ | ------------------------------------------------ | ---------------------------- | --------------------------------------- |
| 纯文档、注释、格式                               | diff 与对应格式检查                              | 构建、行为测试、浏览器       | 影响代码生成、配置或发布内容            |
| 局部纯逻辑、工具函数                             | 受影响的现有测试；适用的类型检查                 | 页面巡检、截图               | 修改公共契约、动态加载、缺少可信测试    |
| 静态文案或局部样式                               | 相关渲染状态的一次实际查看，按需附带运行错误摘要 | 无关交互、整站巡检、无关视口 | 溢出、可访问性、响应式或多语言风险      |
| 前端状态或交互                                   | 对应行为测试；未覆盖浏览器行为时补一条关键流程   | 已有测试覆盖后的人工重演     | DOM、焦点、路由、剪贴板等浏览器特有问题 |
| 后端接口或存储                                   | 对应单元/集成与契约检查                          | 不相关的浏览器流程           | API 兼容性、UI 联动、迁移或权限变化     |
| 认证、权限、数据迁移、安装器、更新器、跨模块依赖 | 按风险扩展集成、故障路径和平台检查               | 不设无条件快速豁免           | 沿用项目强制门槛，已知失败必须处理      |

同一任务可以命中多行，取必要检查的并集。这里的“省略”必须基于明确范围，未知影响不能直接归入低风险。已有测试能够防止目标回归时，不必为每个小修复再增加一个与实现同构的测试。

最低成本的验收选择应该由主 Agent 在理解任务时完成，并配合确定性规则；不要为了省一次检查，再增加一轮独立模型审查。

**六、让规则真正执行，而非不断提醒**

建议在当前架构中逐步增加轻量的验证计划与结果记录，以下是设计草案，并非已实现接口：

```text
本次需要确认：用户修改消息后能保存
风险：局部交互
检查：已有编辑消息测试；若视觉发生变化，再查看受影响画面
停止：必要断言通过，证据仍适用于最终修改，无未解决失败
扩大：测试失败、依赖范围扩大、出现浏览器特有异常
```

运行时保存检查目标、输入指纹、执行命令/工具、断言结果、退出状态、时间、环境身份、证据位置以及跳过原因。结果至少区分“通过、失败、受阻、按范围省略、仍然有效的已有证据”。模型可以解释结果，但普通 `exec` 成功或浏览器动作成功不能自动等同于业务断言通过。

证据复用的指纹应覆盖相关源码、传递依赖、测试文件、配置、锁文件、工具版本和影响结果的环境。未知依赖保守失效；未跟踪文件和当前工作区修改也应纳入；不能只比较提交 SHA、时间戳或命令字符串。视觉证据还需对应页面构建、视口和状态；服务或数据变化可能使旧证据失效。

针对当前守卫，先增加结构化结果与 `not_applicable` 等原因的表达能力，再考虑用其驱动策略。不要简单把更多命令名加入“通过”正则，或为满足正则重跑已经完成的检查。

浏览器执行侧优先做这些具体调整：

- 已知步骤批量执行，最后等待可观察的结果并返回一次证据。
- 默认返回断言、错误摘要和目标区域；仅在有视觉变化或疑点时返回必要图片。
- 等待目标状态，减少固定睡眠；页面未就绪时也不要立刻连续轮询模型。
- 复用身份匹配的预览服务与浏览器会话，失败后从未完成步骤恢复。
- 每轮修复仅使受影响证据失效，不重跑已通过且输入未变的其他检查。
- 保留已有失败，不将预算耗尽、超时或未发现测试标成成功。

**七、适合本仓库的测试筛选方式**

第一步使用显式的受影响测试文件，必要时辅以 Vitest `related`，比直接引入全新调度平台更容易审查。示例仅用于说明策略，本次没有执行：

```bash
npx vitest run packages/pi-adapter/test/system-prompt.test.ts
npx vitest related packages/pi-adapter/src/system-prompt.ts --run
npx playwright test e2e/edit-composer.spec.ts
```

执行前仍需确认当前 workspace、测试发现规则和构建产物状态。`related` 静态关系不覆盖所有运行时耦合，本仓库包入口引用 `dist` 时还需处理源码到产物的关系。无测试被选中时，记录为“没有选出测试”，不能显示为目标行为已通过。

E2E 往往只是通过 URL 访问应用，并不 import 页面源码。因此 `--only-changed` 无法自然推导“组件变了，要运行哪个浏览器场景”。对于这个项目，应采用小型维护映射，例如编辑输入组件对应编辑与草稿流程；公共协议、会话状态和基础设施变化则扩大到相关核心流程。共享文件不能只按目录排除。

CI 可以随后增加路径筛选、确定性检查缓存和隔离后的有限并行。任务级定向验证与仓库级较广回归可以分层，但本仓库目前没有已确认的完整 E2E 周期兜底；如果以后缩减现有 CI 门槛，应同时设计抽检或周期回归，不能假设它已经存在。

**八、用户体验应如何变化**

在实现结束时尽早展示结果与预览，状态明确写“改动已就绪，正在检查保存流程”，而不是让用户等到所有报告整理结束才看到成果。必要检查完成后，给一句可核实的摘要，例如：“已检查编辑保存；本次不涉及手机布局，未执行手机检查。”

必要验证尚未完成时不能宣称任务完全通过。可选的广泛检查若未来放到后台，要有实际任务生命周期和失败回传，不能仅在文案里承诺稍后验证。本次不建议先引入这项复杂度。

常规低风险检查可以制定短时间目标；已有浏览器 60/90 秒规则应升级为可观测预算。到预算时停止新增可选检查；必要检查受阻就显示受阻，已知回归则处理并解释延长原因。高风险任务不套用相同硬上限。

**九、推荐实施顺序与效果判断**

| 优先级 | 工作                                                                             | 为什么先做                                |
| ------ | -------------------------------------------------------------------------------- | ----------------------------------------- |
| P0     | 统一系统提示词、工具说明、前端技能和流程文档；按行为定义浏览器触发条件与停止条件 | 修改面小，直接处理已发现的范围冲突        |
| P0     | 增加任务阶段耗时、验证工具往返、重复取证和环境启动计数                           | 确认瓶颈，避免只优化 token 或测试程序耗时 |
| P1     | 将已有批量能力作为已知流程的默认路径，返回最小证据                               | 减少模型往返，保留验收断言                |
| P1     | 增加结构化检查结果与有效证据复用；引入简单测试映射                               | 减少同一结果重复检查，解释何时可以结束    |
| P2     | 根据测量结果优化 E2E 服务复用、trace/video、CI 筛选和缓存                        | 工程改动较大，收益应由数据决定            |

用固定的一组文案、样式、逻辑、交互和高风险变更任务，保持模型、提示上下文、机器与网络条件尽量一致，分开记录冷启动与热启动，多次比较新旧策略。至少观察：

- 从最后一次实现编辑到交付的耗时中位数与 P95，以及整体任务耗时。
- 收尾阶段模型调用数、浏览器观察次数、重复检查数、服务启动次数。
- 必要检查通过率、未验证比例、交付后回归与用户返工率。
- 扩展回归抽检发现了多少被轻量策略漏掉的问题。

优化标准是：等待和重复工作下降，必要验收与交付质量没有出现可接受范围之外的恶化。先按基线制定目标，不凭模型能力或 GitHub 项目的自报数字推断本项目会快多少。

**十、重点补查：DeepSeek Harness、Codex、Claude**

这几家的材料提供了不同层次的依据：开发仓库的规则说明其维护方式；公开的基础提示词说明一套 Agent 行为设计；示例程序展示可以运行的机制；产品文档描述配置能力。不能把其中任一层直接等同于所有已发布产品、所有模型的默认行为。

**10.1 DeepSeek Harness：最直接的“相关验证，不重复”参考**

[官方 AGENTS.md 第 114 行起](https://github.com/deepseek-ai/deepseek-harness/blob/master/AGENTS.md#L114)明确把局部验证和完整 CI 分开：本地检查与修改面匹配，不默认跑全套，也不因随后 commit 或 push 而重复成功检查。跨仓库影响、诊断 CI 或用户明确要求时才扩大本地演练。

[推送前检查技能](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/skills/dsh-pre-push-checks/SKILL.md)进一步要求：选择能捕捉目标回归的最窄检查；公共契约变化才增加相邻测试；合并新基线后只重跑失效证据；检查测试实际选中了多少用例。它还明确区分“测试选择”与“覆盖率统计范围”，并提醒配置驱动、子进程、worker 和产物依赖需要显式选测。

对 Pi-Wuming 的启发是把“需要证明哪个行为”作为基本单位，而非统一堆叠 typecheck、build、unit、browser、screenshot。已有 CI 或 hook 刚刚完成的同一份检查，在输入仍一致时可以作为证据复用；跨操作系统或不同依赖环境的运行则不自动等价。

[DeepSeek 测试策略](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/testing.md)采用录制的 Session 做不需要 API key 的回放，覆盖真实 harness 组装和持久化输出；同时明确真实模型调用仍有不可替代的价值。Pi-Wuming 的工具协议、流式响应、恢复流程可以评估类似回放，以减少反复请求真实模型或手动走 UI。回放能验证固定输入下的系统行为，不能证明模型会遵守新提示词，因此提示词、供应商与 Agent 行为变化仍需小规模真实验收。

另外，[Agent loop 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/README.md)说明动态上下文没变化就不重复注入，重试复用已组装请求，并明确没有内建 turn 总预算。可借鉴它的事件与上下文设计，但不能把它描述成已经提供通用的防耗时验证策略。

**10.2 Codex：从窄检查开始，同时给扩展设明确条件**

[公开基础提示词的验证段落](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md#L149)建议先测本次修改最直接涉及的代码，再考虑更广测试；不处理无关缺陷；没有测试体系的项目不贸然新增体系；格式化修复也有停止边界。

可借鉴其对任务范围的约束，但“再考虑更广测试”应在 Pi-Wuming 中具体化：只有依赖范围扩大、遇到失败、发现未覆盖风险或项目要求时才扩展。否则模型可能把一次成功检查理解为下一轮更大检查的起点。

此次没有验证该基础模板与当前商业 Codex 桌面端、服务端或每个模型实际使用提示词的对应关系，也未找到可据此断言的通用自动风险裁剪机制。

**10.3 Claude Code：停止钩子既能兜底，也可能放大等待**

[官方插件的 hook 示例](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/plugin-dev/skills/hook-development/references/patterns.md)包含结束前强制检查测试、构建的模板。这是可选扩展范例，不是“Claude Code 默认一定这样做”的证据。

[官方 Stop hooks 文档](https://code.claude.com/docs/en/hooks#stop)说明钩子可以使模型继续运行，并提供 `stop_hook_active` 供防止重复阻塞。截至本次查阅，文档也描述连续续跑次数上限，但调用工具会重置该计数。因此不能仅凭这一上限保证“测试 → Stop → 再测试”的总耗时受限。

Pi-Wuming 不宜把当前非阻塞 verification warning 直接改成“只要不满意就让模型再跑一轮”的强制钩子。建议先让完成检查读取已经收集的结果：必要目标满足就结束；没有新修改、没有新失败、没有新证据时不再自动扩展；真正受阻的检查明确汇报。若以后增加阻塞机制，必须同时定义任务级累计预算与不可循环的退出条件。

**10.4 Anthropic 的高价值提速实现：批量动作与稳定上下文**

[computer-use 最佳实践示例](https://github.com/anthropics/claude-quickstarts/tree/main/computer-use-best-practices)提供批量电脑/浏览器动作，并在[循环源码](https://github.com/anthropics/claude-quickstarts/blob/main/computer-use-best-practices/computer_use/loop.py)里对特定单动作调用追加批量提示；同时记录每轮耗时与缓存命中。其截图历史管理采用分段裁剪，以避免每轮删掉不同旧图导致提示前缀不断变化。

这带来两个独立优化面：一是减少模型必须参与的轮数；二是降低每轮重复处理上下文的成本。Pi-Wuming 已有批量动作，先测实际使用率最划算。截图裁剪与供应商缓存则应先检查当前 adapter 和上下文管理实现，不能为了减少图片条数反而破坏缓存，或丢失当前必要的视觉证据。

这些技术都不需要再加入一个“测试 Agent”来判断每一步。对简单收尾，额外模型调用本身可能抵消节省的时间。

**10.5 不要把长期自主开发示例当成小修改默认值**

Anthropic 的[长期 Agent harness 文章](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)针对跨上下文、跨会话构建完整应用，强调恢复进度与实际端到端验收。对应的[公开 coding prompt](https://github.com/anthropics/claude-quickstarts/blob/main/autonomous-coding/prompts/coding_prompt.md)要求会话开始先检查 1–2 个核心功能，功能实现后通过 UI 验收，并频繁截图。

它提供的是长任务可靠性方案，而非最短交付延迟方案。适合借鉴功能清单、已验证状态、稳定启动方式；不宜把频繁浏览器巡检推广到注释、局部工具函数或已经有可靠回归测试的小修复。强模型与更轻 harness 是否足够，需要按任务种类实测，而不是从旧示例或模型声誉推断。

**补查后的建议调整**

优先参考 DeepSeek 的验证选择和证据复用规则，配合 Anthropic 的批量浏览器及上下文处理方式；用 Codex 的范围约束防止任务顺手扩大。继续保留必要验收，先消除重复执行与无依据的扩大。录制回放适合作为 Pi-Wuming 自身协议和恢复测试的后续优化，通用自动审查 Agent 和强制 Stop 循环不列入首批工作。
